# Дизайн: классификатор товаров по ПП № 1875 (Задача 2)

**Команда:** «Дрын Тим» (5 человек) · **Кейс-чемпионат:** AI Procurement Copilot, B2B-Center
**Дата:** 2026-10-14 · **Сдача этапа 1:** ~31.10.2026 (уточнить в общем чате)

## 1. Цель и критерии успеха

Тендерный специалист вводит наименование товара (или список до 100 штук) и получает
вердикт: подпадает ли товар под национальный режим по ПП РФ № 1875 от 23.12.2024,
под какой именно режим, по какому пункту, и насколько система уверена.

Критерии приёмки организаторов (на каждый должно быть доказательство в README и видео):

| № | Критерий | Метрика | Чем закрываем |
|---|---|---|---|
| 1 | Точность | ≥ 85% на тестовом датасете (20 товаров) | Скрипт `eval` на собственном наборе ≥150 товаров |
| 2 | Время ответа | 1 запрос < 5 с | Синхронный эндпоинт, модели прогреты при старте, бенчмарк |
| 3 | Массовая обработка | 100 товаров < 2 мин | Celery + батчинг эмбеддингов/реранкера, кэш, бенчмарк |
| 4 | Обновление базы НПА | без передеплоя | Загрузка новой редакции через UI/API → фоновая переиндексация, версии |
| 5 | Уверенность | % для каждого товара | Калиброванный score реранкера |
| 6 | Ссылки на НПА | каждый результат ссылается на пункт | Приложение + номер пункта + текст пункта + ссылка на источник |
| 7 | Архитектура | `docker-compose up --build` | Один compose-файл, веса моделей запекаются в образ |

Принятые решения (согласованы с командой):
- ИИ-основа **полностью локальная** (работает без интернета и ключей на CPU); **опциональный LLM-режим** включается ключом в `.env`.
- Выдача — **полный вердикт**: код ОКПД2 + режим (ЗАПРЕТ / ОГРАНИЧЕНИЕ / ПРЕИМУЩЕСТВО / НЕ ПОДПАДАЕТ) + приложение и пункт ПП + уверенность + топ-3 альтернативы.
- Ввод: текстовое поле (строка = товар) **или** загрузка `.xlsx/.csv`; экспорт результата в `.xlsx`.
- Подход **Б**: товар → код ОКПД2 (семантический поиск) → детерминированная сверка с ПП 1875.

Допущения:
- У жюри может не быть GPU и интернета после сборки → CPU по умолчанию, GPU — опциональный профиль.
- Команда — студенты 2 курса; основной код пишет ИИ, команда ведёт датасет, тестирование, видео и защиту. Проект должен быть понятен им к очному этапу (48 ч доп. задания).

## 2. Архитектура

```
              ┌───────────── docker-compose ─────────────┐
 Браузер ──▶  │ web (React+Vite, nginx) ──/api──▶ api     │
              │                              (FastAPI)    │
              │                     Redis ◀────┘   │      │
              │                       │            ▼      │
              │                    worker ──▶ Postgres    │
              │                   (Celery)    + pgvector  │
              └───────────────────────────────────────────┘
```

Сервисы:
- **web** — React + Vite + TypeScript, собирается в статику, раздаётся nginx; nginx проксирует `/api` → `api`.
- **api** — FastAPI. Одиночная классификация синхронно; пакеты — постановка задачи в Celery; экспорт; загрузка НПА; Swagger на `/docs`.
- **worker** — Celery: пакетная классификация, разбор и индексация новой редакции НПА, первичная загрузка ОКПД2.
- **redis** — брокер и backend результатов Celery.
- **db** — PostgreSQL 16 + pgvector.

Общий Python-пакет `classifier` (используется и `api`, и `worker`), модули с одной ответственностью:
- `embedder` — текст → вектор (кандидаты: `intfloat/multilingual-e5-base`, `multilingual-e5-large`, `BAAI/bge-m3`; выбор по замеру точности/скорости).
- `retriever` — top-K кодов ОКПД2 из pgvector (по официальным наименованиям и синонимам, агрегация по коду).
- `reranker` — кросс-энкодер (кандидат `BAAI/bge-reranker-v2-m3`), выбирает лучший код, даёт score.
- `confidence` — превращает score в % уверенности (калибровка на тестовом наборе).
- `matcher` — **без ИИ**: сверяет код ОКПД2 с позициями активной версии ПП (иерархия кодов, исключения), возвращает режим и пункт.
- `llm` (опционально) — при наличии `LLM_API_KEY` выбирает код из топ-5 и пишет объяснение по-русски; при ошибке/таймауте — молча откат на локальный результат.
- `npa_parser` — разбор файла редакции ПП (docx/xlsx/pdf) в позиции.

Модели скачиваются на этапе `docker build` и хранятся в образе → после сборки интернет не нужен.
GPU — отдельный файл `docker-compose.gpu.yml` (для демо на RTX 3050); по умолчанию CPU.

## 3. Конвейер классификации

1. **Нормализация**: нижний регистр, раскрытие частых сокращений («ноут» → «ноутбук», «шт», единицы измерения убираются), удаление артикулов-шумов.
2. **Эмбеддинг** запроса (`query:` префикс для e5).
3. **Поиск**: top-20 кодов ОКПД2 по косинусной близости среди официальных наименований и синонимов.
4. **Переранжирование**: кросс-энкодер оценивает пары (товар, наименование кода), выбирается лучший; топ-3 альтернативы сохраняются.
5. **(Опц.) LLM**: выбор среди топ-5 + объяснение.
6. **Сверка с ПП** (`matcher`): код ищется в позициях активной версии с учётом иерархии (позиция `26.20` покрывает `26.20.11.110`), исключений и уровня детализации. Если найдено несколько позиций — показываются все (товар может быть одновременно в разных приложениях).
7. **Уверенность** = калиброванная вероятность верного вердикта по ПП; при < 80% (`needs_review_threshold`) строка помечается «⚠ проверьте вручную».

Кэш: результат по нормализованному наименованию + версии НПА хранится в Postgres; повторные товары не пересчитываются.

## 4. Данные

Источники (проверены в фазе 0, см. `docs/npa-structure.md`; базовая редакция — открытые ежедневно обновляемые выгрузки из Кодекса и Росстата, конвертер `backend/scripts/import_open_data.py`; формат загрузки новой редакции — JSON или XLSX):
- **ОКПД2 (ОК 034-2014)** — открытые выгрузки CSV/XLSX (~20 тыс. позиций, иерархия по коду).
- **ПП № 1875 от 23.12.2024** — официальный текст с приложениями (publication.pravo.gov.ru / pravo.gov.ru). Перед парсингом **проверить фактическую структуру приложений** (какие перечни, какие режимы, как оформлены коды и исключения) и зафиксировать её в `docs/npa-structure.md`.
- **Синонимы** — генерируются один раз при разработке (LLM) для кодов, встречающихся в ПП, и для популярных товарных групп; хранятся в репозитории как `data/okpd2_synonyms.csv`, в рантайме LLM не нужен.

Таблицы:
- `okpd2_code(code PK, title, parent_code, level)`
- `okpd2_text(id, code FK, text, kind[official|synonym], embedding vector)`
- `npa_version(id, title, source_url, uploaded_at, is_active, status[parsing|ready|failed])`
- `npa_item(id, version FK, appendix, item_no, codes text[], title, regime, quota int null, exclusions text[], note, has_conditions bool)` — структура уточнена по факту в `docs/npa-structure.md`: у позиции список кодов, у прил. 3 доля российских товаров, исключения в источнике записаны текстом (флаг `has_conditions`).
- `classification_cache(norm_name, npa_version, result jsonb)`
- `job(id, status, total, done, created_at)` / `job_item(job FK, idx, input, result jsonb)`

Обновление базы НПА без передеплоя: загрузка файла → `npa_version` в статусе `parsing` → worker парсит → валидация (позиции найдены, коды валидны) → `ready` и атомарное переключение `is_active`; при ошибке старая версия остаётся активной, статус `failed` с причиной. Кэш инвалидируется сменой версии.

Тестовый набор: `data/eval/testset.csv` (`name, okpd2_expected, regime_expected, appendix_item_expected, source`). Собирает команда, ≥150 товаров из реальных закупок (zakupki.gov.ru), включая «грязные» названия.

## 5. Интерфейс

Один экран на русском, крупные элементы:
- поле ввода (строка = товар) + кнопка «Загрузить Excel/CSV» + «Проверить»;
- прогресс «Обработано N из M» для пакета;
- таблица: товар · код ОКПД2 (+ наименование) · режим цветом (красный — запрет, жёлтый — ограничение, синий — преимущество, зелёный — не подпадает) · пункт ПП (ссылка, раскрывает текст пункта) · уверенность % · ⚠ при низкой уверенности;
- раскрытие строки: объяснение, топ-3 альтернативы;
- «Скачать Excel»;
- страница «База НПА»: активная версия, история, загрузка новой редакции, статус разбора.

## 6. API

- `POST /api/classify` `{ "name": "..." }` → результат (синхронно)
- `POST /api/classify/batch` `{ "names": [...] }` или multipart-файл (.xlsx/.csv) → `{ "job_id" }`; лимит 100
- `GET /api/jobs/{id}` → статус, прогресс, результаты
- `GET /api/jobs/{id}/export.xlsx`
- `GET /api/npa/versions`, `POST /api/npa/upload`, `GET /api/npa/items/{id}`
- `GET /api/health` — готовность моделей и БД

Формат результата:

## 7. Обработка ошибок

- Пустые/мусорные строки пропускаются с пометкой, а не валят пакет.
- > 100 товаров → 422 с понятным сообщением.
- Ошибка одного товара в пакете не останавливает остальные.
- LLM недоступен → локальный результат без объяснения.
- Битый файл НПА → версия `failed`, активная версия не меняется.
- Модели не прогреты → `/api/health` возвращает `starting`, UI показывает «Система запускается».

## 8. Тестирование и метрики

- `pytest`: unit-тесты `matcher` (иерархия, исключения, несколько приложений) — приоритет №1; `npa_parser` на фикстуре; API-тесты.
- `scripts/eval.py`: точность по коду ОКПД2 (top-1, top-3) и по вердикту ПП, список ошибок → `reports/eval.md`.
- `scripts/bench.py`: латентность 1 запроса (p50/p95) и время 100 товаров на CPU и GPU.
- Ревью кода: цикл Claude ↔ Codex (adversarial-review).

## 9. Риски

| Риск | Мера |
|---|---|
| 100 товаров на CPU > 2 мин | Батчинг, кэш, уменьшение K для реранкера, лёгкая модель эмбеддингов; замер в первые дни |
