# Задача 2 · Классификатор товаров по ПП РФ № 1875 — пакет дообучения модели

Кейс-чемпионат B2B-Center «AI Procurement Copilot», задача 2. Пакет дообучает модель поиска по ОКПД2 для бэкенда
команды ([kla1m3n/b2b-center](https://github.com/kla1m3n/b2b-center)) и содержит все данные для этого.

**Коротко:** бэкенд по наименованию товара находит код ОКПД2, по коду правилом определяет позицию ПП 1875 и выдаёт
вердикт (запрет / ограничение / преимущество / не подпадает) с уверенностью. Точнее всего на результат влияет первый
шаг — поиск кода. Его делает эмбеддер. Пакет улучшает этот шаг тремя способами:

1. **Дообучение эмбеддера** на реальных формулировках из закупок. Переключатель `MODEL`: `e5-large` — та же модель, что
   сейчас в бэкенде; `frida` — маленькая `rubert-mini-frida`, примерно в 6 раз быстрее и на ~2 ГБ легче.
2. **doc2query** — LLM пишет для каждого кода ОКПД2 типичные формулировки заказчиков, они добавляются в индекс поиска
   рядом с синонимами. Модель от этого не меняется, скорость ответа тоже.
3. **ONNX + int8** — упаковка модели для CPU с замером скорости и точности против PyTorch.

Тексты для обучения и doc2query пишет GigaChat API — скриптом на своём компьютере (раздел 6а); ноутбук берёт
готовые файлы из датасета и сам LLM не запускает. Новая модель подключается к бэкенду настройкой `EMBED_MODEL`, формулировки doc2query —
файлами в `data/`.

### Быстрый старт

1. Загрузить папку `kaggle_dataset/` в Kaggle как датасет `pp1875-data` (раздел 6, шаг 1).
2. *(По желанию)* Сгенерировать тексты через GigaChat: `python tools/gigachat_generate.py ...` (раздел 6а) и
   добавить `synth.csv` и `okpd2_generated_raw.csv` в датасет.
3. Импортировать `pp1875_kaggle.ipynb`, включить GPU T4 и Internet, выбрать `MODEL` и кеши в «Константах», Run All.
4. Скачать `artifacts.zip`, разложить модель и `backend_data/` в бэкенд (раздел 7).
5. Прогнать `eval.py` бэкенда и решить, оставлять ли новую модель (раздел 7, «Когда оставлять»).

## 3. Как это работает

```
наименование ─► нормализация, исправление опечаток (бэкенд)
             ─► поиск по смыслу: эмбеддер (ДООБУЧЕННЫЙ) в pgvector  ┐  индекс: наименования кодов
             ─► поиск по словам: BM25                              ┴► + синонимы + формулировки doc2query
                                                                    └► объединение (RRF) ─► лучший код ОКПД2
             ─► сверка с ПП 1875 правилом по иерархии кода (без ИИ) ─► позиции приложений 1–3, вердикт
             ─► уверенность = калиброванная вероятность верного вердикта; < 0,8 → «проверьте вручную»
```

Почему дообучаем только поиск. Вердикт по ПП определяется правилом по коду, а не нейросетью: позиция подходит товару,
если её код — начало кода товара, а код категории `XX.XX.XX.XX0` охватывает подкатегории `XX.XX.XX.XXX`. Поэтому
ошибка в вердикте почти всегда — ошибка в найденном коде. В самой модели нет знаний о ПП, поэтому новая редакция
постановления — это только новый файл базы, без переобучения.

## 4. Данные для обучения

**Выборка v2 (`train_v2.csv`, по умолчанию).** ~140 тыс. пар «наименование → код» с колонками `text, okpd2,
negative_code, source`: КТРУ, синтетика GigaChat, ~470 «закупочных» наименований, синонимы, наименования кодов и
искажения как в ЕИС (шаблоны «Поставка товара: …», артикулы, количество, ГОСТ, опечатки, CAPS). У каждой строки —
трудный негатив: соседний код той же группы, часто с другим режимом ПП; ноутбук берёт его в половине случаев
(`V2_NEG_SHARE`), остальным негатив подбирает модель. Собрана из `train_full.csv` скриптом `data_build/clean_v2.py`:
убраны 503 строки, почти совпадающие с dev/testset/stress/holdout/validation (≥ 70% слов), и 6 тыс. пар
«наименование кода → то же наименование» у кодов, где есть другие примеры. Синтетика и искажения уже внутри, поэтому
`USE_SYNTH = False`, `AUGMENT_FRAC = 0`. Старая выборка: `TRAIN_FILES = ["train_pairs.csv"]`, `USE_SYNTH = True`,
`AUGMENT_FRAC = 0.3`.

Таблица ниже — состав старой выборки.


| Источник | Пар после фильтров | Что даёт |
|---|---|---|
| КТРУ (`train_pairs.csv`) | ≈5 100 (не больше 40 на код) | Настоящие формулировки товаров с характеристиками. Все пары — товары из перечней ПП |
| КТРУ с кодом-группой | ≈960 | 10% пар КТРУ записаны кодом группы (`10.12.10.000` = группа `10.12.10`) или кодом старой редакции. Код нижнего уровня внутри группы выбирает исходная модель (раньше такие пары молча выбрасывались) |
| Синонимы бэкенда | ≈620 | Бытовые названия ходовых товаров («lada», «дсп», «щебень») |
| Наименования кодов ОКПД2 | ≈8–14 тыс. | «Наименование кода → код» — только для кодов без других примеров: каждый код хоть раз в обучении, но тривиальные пары не размывают батчи |
| Синтетика LLM | до ~52 000 (6 500 кодов × 8) | По приоритету: (1) коды ПП без реальных пар или с < 5, (2) их «соседи» вне ПП — трудные негативы для «не подпадает», (3) остальные коды ПП; плюс 10% случайных кодов. Покрывает 5 340 из 5 629 кодов ПП и все 952 «соседа» |
| Аугментации | +30% | Опечатки, «(или эквивалент)», «, шт», обрезка характеристик, пропуск слова |

Наименования из `dev.csv` и тестовых наборов **удаляются** из обучения — без учёта регистра (в КТРУ и синонимах было
31 наименование из dev в нижнем регистре: «ноутбук», «принтер», «коммутатор»). Тексты, которые в данных ведут к разным
кодам (78 синонимов вроде «бинт», «ip телефон»), из обучения убраны, в индексе поиска остаются.

**Как синтетика отбиралась раньше и почему это исправлено.** Брались первые 3 000 кодов ПП по порядку классификатора —
только разделы 10–22. Компьютеры (26), машины (28), медизделия (32) и ещё 2 600 кодов ПП не попадали, «соседи» вне ПП
не попадали совсем. Отбор, карточки кодов и промпты теперь в `pp1875_core.py` — общие для ноутбука (проверка полноты)
и скрипта GigaChat.

### doc2query — тексты для индекса, а не для обучения

| Что | Сколько | Как |
|---|---|---|
| Формулировки для всех ~15 400 кодов | 6 на код, после чистки обычно меньше | Для кодов с синтетикой берутся её строки, для остальных LLM пишет новые |
| Чистка | — | Убираются совпадения с dev/тестом (утечка), тексты, которые LLM дала разным кодам, и тексты, для которых исходная модель не находит их код даже в top-50 (ошибки LLM) |
| Решение «включать или нет» | — | После обучения ноутбук сравнивает на `dev.csv` индекс с формулировками и без. Если с ними хуже, они не попадают в экспорт |

У кода в индексе теперь несколько текстов. Как и в бэкенде (`retriever.py`), код получает оценку своего **лучшего**
текста: запрос «ноутбук 15.6 i5» находит формулировку «ноутбук 15.6 дюйма» и через неё код 26.20.11.110.

## 5. По каким критериям проходит обучение

### Что оптимизируется

- **Задача — поиск, а не классификация.** Модель учится ставить вектор наименования ближе к вектору наименования его
  кода ОКПД2, чем к остальным кодам. Новые коды ОКПД2 поэтому работают без переобучения, достаточно пересчитать индекс.
- **Функция потерь — contrastive (InfoNCE).** В батче из 64 примеров для каждого наименования верный код соревнуется с
  127 неверными: кодами остальных примеров батча и **трудными негативами**. Трудный негатив — похожий, но неверный код
  из top-15 поиска исходной модели («Конверты» для «Бумага А4»). Масштаб сходства — 20.
- **Без ложных негативов.** Если у двух примеров в батче одинаковый код, совпадение не считается ошибкой. Это важно для
  КТРУ, где на один код много позиций.
- **Документ — чистое наименование кода**, ровно как в индексе бэкенда. Добавление названий разделов, по замерам
  команды, ухудшало поиск. Метрики считаются по индексу, как в бэкенде: наименования + синонимы (+ doc2query).

### Настройки (`PRESETS` в ячейке «Константы»)

| Параметр | `e5-large` | `frida` | Почему |
|---|---|---|---|
| Эпохи | 2 | 4 | Большой модели хватает двух, больше — риск подстроиться под синтетику. Маленькая учится быстрее, эпохи дешёвые |
| Батч | 64 (+ 64 трудных негатива) | 128 (+ 128) | Больше негативов — лучше различаются соседние коды. e5-large влезает в T4 только с gradient checkpointing |
| Скорость обучения | 1e-5 | 5e-5 | Бережно для большой модели; маленькой нужен шаг крупнее |
| Gradient checkpointing | вкл. | выкл. | Экономит память ценой ~30% скорости — маленькой модели не нужен |
| Общее | | | Разогрев 10% и линейное затухание, длина текста 64 токена, fp16 (AMP), ограничение градиента 1.0 |

Сравнить модели: запустите ноутбук дважды, с `MODEL = "e5-large"` и `MODEL = "frida"`, и сравните таблицы «Итоги» и
`metrics.json`. Синтетику и формулировки второй раз не генерируйте — укажите кеши (раздел 6).

### Метрики (печатаются после каждой эпохи)

| Метрика | Что значит |
|---|---|
| **Val Verdict** | Доля товаров `dev.csv`, у которых верный вердикт по ПП. Это главный критерий жюри (≥ 85%). Считается как в `eval.py` бэкенда: для кода-группы засчитывается вердикт любого кода группы |
| **Val Code@1** | Найденный код лежит внутри эталонного (то же правило иерархии, что в сверке с ПП) |
| **Val Code@20** | Верный код среди 20 кандидатов поиска — «потолок» для всей системы |
| **Test Verdict** | То же на `testset` + `stress` + `validation` — только для информации |
| pp_exact, ECE | Точный набор позиций ПП; честность уверенности |

### Как выбирается итоговая модель

1. **Эпоха 0** — исходная модель без обучения: от неё и отсчёт.
2. После каждой эпохи на `dev.csv` считается оценка **вердикт + код@1 + 0,5 · код@20** по индексу **без** doc2query
   (качество самой модели). Код@20 добавлен потому, что на 88 товарах вердикт и код@1 часто дают ничью.
3. При равной оценке берётся обученная эпоха. Исходная модель экспортируется, только если все эпохи строго хуже.
   (Раньше ничья оставляла исходную модель — так в одном из запусков пропала рабочая дообученная модель.)
4. Про doc2query решается отдельно, после обучения: формулировки попадают в экспорт, только если с ними **не хуже и
   на dev, и на тестовых наборах** (допуск 0,01). Только по dev нельзя: на одном из запусков dev показал +1 товар,
   а тест — вердикт 94,8 → 83,2%.
5. `holdout.csv` не участвует. Финальное решение «подключать или нет» — `eval.py` бэкенда (раздел 7).

### ONNX + int8 (последняя ячейка)

Модель экспортируется в ONNX и квантуется в int8 (веса в ~4 раза меньше). Это делает скрипт `onnx_export.py`
**отдельным процессом**: установка optimum может сменить версию transformers, а библиотеки, уже загруженные в
ноутбук, от такой подмены ломаются. К этому моменту модель и `artifacts.zip` уже сохранены; если ONNX не получится,
они не пострадают. Ячейка печатает:

| Таблица | Что в ней |
|---|---|
| Скорость на CPU | 1 запрос и 100 запросов для PyTorch fp32, ONNX fp32 и ONNX int8, размер модели, ускорение |
| Совпадение векторов | средний и минимальный косинус между векторами int8 и PyTorch (≈ 0,99 и выше — норма) |
| Точность | dev и тест для двух вариантов: **int8-запросы + fp32-индекс** (индекс бэкенда не пересчитывается) и **всё в int8** (оценка по top-50 кандидатам — пересчитать весь индекс на CPU долго) |

Ускоряется только эмбеддинг запроса. По замерам бэкенда это меньшая часть времени ответа: 0,17 с на товар внутри
процесса против 0,46 с через HTTP API. Поэтому ONNX имеет смысл как последний шаг поверх выбора модели и doc2query.

### Пример вывода

```
До обучения, индекс без doc2query | Val: {'code_top1': 0.41, 'code_top20': 0.75, 'verdict': 0.80, ...}
До обучения, индекс с doc2query   | Val: {'code_top1': 0.44, 'code_top20': 0.79, 'verdict': 0.82, ...}
Epoch [01/02] | Train Loss: 1.2345 | Val Code@1: 0.4773 | Val Code@20: 0.8068 | Val Verdict: 0.8409 | Test Verdict: 0.9010
Epoch [02/02] | Train Loss: 0.9876 | Val Code@1: 0.5000 | Val Code@20: 0.8182 | Val Verdict: 0.8636 | Test Verdict: 0.9109
doc2query на dev: с формулировками 1.3636 vs без 1.3409 (вердикт + код@1)
```
*(Цифры условные: реальных запусков ещё не было.)* В ноутбуке поиск идёт **без** BM25, исправления опечаток и правил
бэкенда, поэтому абсолютные цифры ниже, чем в `reports/` бэкенда. Сравнивайте «до» и «после» внутри ноутбука,
а итог — только через `eval.py` бэкенда.

## 6а. Тексты через GigaChat API

Ноутбук обучается на текстах, которые заранее пишет GigaChat: синтетика для обучения (`synth.csv`) и формулировки
doc2query для индекса (`okpd2_generated_raw.csv`). Их делает скрипт `tools/gigachat_generate.py`; отбор кодов, задания и
формат он берёт из `pp1875_core.py` датасета. Делается один раз: ~11–13 ч на Pro (можно на ночь), ~5 млн токенов —
~13% бесплатного лимита Pro. Нужны ключ GigaChat API и сертификат НУЦ Минцифры. (Раньше тексты мог писать и Qwen
прямо в ноутбуке — убран: тексты GigaChat лучше, а генерация на GPU Kaggle занимала 4–5 ч каждого запуска.)

**Почему на своём компьютере, а не в Kaggle:** серверы Kaggle за рубежом, и доступность API GigaChat оттуда не
проверена. GPU для этого не нужен.

**Что нужно:**
1. **Ключ авторизации.** developers.sber.ru → Studio → создать проект GigaChat API → «Получить ключ». Окно покажет
   Client ID, Client Secret и **Ключ авторизации** (строка Base64) — нужен последний; он показывается **один раз**.
   Ключ — это личный доступ: только в переменную окружения или скрытый ввод, не в файлы, git, чаты и логи.
   Если ключ где-то засветился, сгенерируйте в кабинете новый — старый перестанет работать.
2. **Сертификат НУЦ Минцифры.** API работает на российском сертификате. Он уже лежит в
   `certs/russian_trusted_root_ca.pem` (скачан с Госуслуг: `https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt`,
   субъект `CN=Russian Trusted Root CA`, SHA-1 `8FF915CCAB7BC16F8C5C8099D53E0E115B3AEC2F`, действует до 2032 г.).
   Файл должен быть в формате **PEM** (начинается с `-----BEGIN CERTIFICATE-----`). Двоичный `.cer` переводится
   так: `certutil -encode russian_trusted_root_ca.cer russian_trusted_root_ca.pem`.
3. **Python 3.10+** с `requests pandas numpy`: `pip install requests pandas numpy`. Если `python` — сборка MSYS2
   (`C:\msys64\...`) без pip, ставьте пакеты через pacman:
   `pacman -S mingw-w64-x86_64-python-requests mingw-w64-x86_64-python-pandas mingw-w64-x86_64-python-numpy`.

**Запуск** из папки `training/kaggle/` (PowerShell):

```powershell
$env:GIGACHAT_CREDENTIALS = Read-Host "Ключ"     # действует до закрытия окна; без переменной скрипт спросит ключ сам
python tools/gigachat_generate.py --data kaggle_dataset --dry-run                                            # оценка
python tools/gigachat_generate.py --data kaggle_dataset --ca-bundle certs\russian_trusted_root_ca.pem --limit 20 --out gigachat_trial   # проба
python tools/gigachat_generate.py --data kaggle_dataset --ca-bundle certs\russian_trusted_root_ca.pem                                  # всё
```

cmd: `set GIGACHAT_CREDENTIALS=...`; Linux/macOS: `export GIGACHAT_CREDENTIALS=...` и `certs/...` вместо `certs\...`.

Пробу пишите в отдельную папку (`--out gigachat_trial`) или удалите `gigachat_out/` перед полным запуском:
продолжение после обрыва пропускает коды, которые уже есть в файле, и пробные строки остались бы в результате.

Результат — папка `gigachat_out/` с `synth.csv` и `okpd2_generated_raw.csv`. Добавьте оба файла в датасет
`pp1875-data` (New Version) — имена по умолчанию уже стоят в `SYNTH_CACHE` и `DOC2Q_CACHE`. Запуск GigaChat
доведите до конца: ноутбук сам ничего не догенерирует и напишет, сколько кодов из отбора без строк. Скрипт и ноутбук
должны работать с одним и тем же `pp1875_core.py`, иначе отбор кодов разойдётся.

| Параметр | По умолчанию | Что значит |
|---|---|---|
| `--model` | `GigaChat-2-Pro` | `GigaChat-2` (Lite) быстрее; `GigaChat-2-Max` лучше и медленнее |
| `--what` | `all` | `synth` или `doc2query` — только одну часть (doc2query берёт готовую синтетику из той же папки) |
| `--batch-synth`, `--batch-d2q` | 3, 8 | кодов в одном запросе: меньше запросов, ответ просится в JSON. Если JSON не разобрался, эти коды переспрашиваются по одному |
| `--limit` | 0 | только первые N кодов — проба |
| `--scope` | `GIGACHAT_API_PERS` | для юрлица `GIGACHAT_API_B2B` / `GIGACHAT_API_CORP` |
| `--out` | `gigachat_out` | куда писать файлы; при повторном запуске укажите ту же папку |
| `--oauth-url`, `--api-url` | `ngw.devices.sberbank.ru`, `gigachat.devices.sberbank.ru` | адреса API. Если пробный запуск не авторизуется, проверьте актуальные адреса в документации Сбера (в новых примерах встречается `api.giga.chat`) |

**Токены и время** (замерено пробой на 20 кодах, `GigaChat-2-Pro`):

| Этап | Кодов | Скорость | Время | Токенов |
|---|---|---|---|---|
| Синтетика | 6 500 × 8 строк | ~15 кодов/мин (запрос на 3 кода ~10–20 с) | ~7 ч | ~2,7 млн |
| doc2query | ~8 900 | пачки по 8 кодов | ~4–5 ч | ~2,4 млн |
| **Итого** | | | **~11–13 ч** | **~5 млн** |

Цифры пересчитаны с пробы на 20 кодах под новый отбор (6 500 кодов по 8 строк вместо 3 600 по 12).

`--dry-run` печатает оценку токенов заранее. Бесплатно физлицу на 12 месяцев дают 250 млн токенов Lite, 40 млн Pro и
25 млн Max. Физлицу API даёт **один поток**: запросы идут по очереди, несколько копий скрипта только получат HTTP 429.
Скрипт печатает прогресс, токены и оставшееся время.

**Железо на скорость не влияет.** Почти всё время скрипт ждёт, пока модель Сбера сгенерирует ответ на их
серверах; локально — только сборка промпта и запись CSV. Нужны компьютер в РФ, стабильный интернет и
**отключённый спящий режим** на время запуска. Быстрее можно только моделью Lite (`--model GigaChat-2`, качество ниже —
сначала проба) или меньшим числом строк на код.

**Качество текстов.** Первая проба со старыми заданиями показала типичные ошибки: для кодов услуг
модель писала товары (сбор отходов → «контейнеры ТБО», «урна уличная»), строки уходили в соседние коды (ОС →
SQL Server; местная связь → «прокладка кабелей»), почти в каждой строке был бренд, часть брендов выдумана.
Поэтому задание теперь содержит:

- **карточку кода:** название, вид — `[товары]`, `[услуги]` или `[работы]` (по началу названия) — и до 4 ближайших
  соседних кодов с пометкой «не путать с»;
- **правила:** для услуг и работ — именно услуги, а не оборудование и расходники; ничего из кодов «не путать»;
  не пересказывать название кода перестановкой слов; бренд и модель — не больше чем в трети строк и только настоящие;
  в doc2query — без общих фраз, подходящих к любому коду.

Повторная проба на тех же 20 кодах: услуги остаются услугами, уход в соседние коды стал редким, выдуманных марок
меньше. Осталось: изредка соседний код (у сбора отходов — «утилизация», «переработка»), выдуманные модели у редких
товаров (таксофоны), спорные коды вроде `37.00.20.000` «Отстой сточных вод». Часть такого шума отсеет фильтр
doc2query в ноутбуке (`DOC2Q_FILTER_K`). Промпт стал длиннее — токенов на ~60% больше, время почти то же.

Задания лежат в `pp1875_core.py`.

**Обрыв, ошибка, Ctrl+C:** каждый ответ сразу дописывается в файл. Запустите ту же команду ещё раз — готовые коды
будут пропущены. Повторы при сбоях сети, HTTP 429 и 5xx — автоматически; токен доступа обновляется сам.
Если запрос заблокирован фильтром тем, код помечается пустой строкой и пропускается.

**Типичные ошибки:**

| Сообщение | Что делать |
|---|---|
| `Ошибка сертификата` | не указан или не тот файл в `--ca-bundle` |
| `Авторизация не прошла: HTTP 401` | неверный ключ или `--scope` (физлицо — `GIGACHAT_API_PERS`) |
| `HTTP 402` | закончились токены выбранной модели — сменить `--model` или докупить пакет |
| `HTTP 404` на запросе | неверное имя модели или адрес API |

## 7. Подключение модели к бэкенду b2b-center

Бэкенд (ветка `main`) уже работает на ONNX: `EMBED_BACKEND=onnx` по умолчанию, модель по умолчанию —
`BOBUS2317/e5-large-pp1875-onnx`. Код менять не нужно, новая модель подключается через `.env`. Ноутбук выдаёт
`artifacts.zip` **только с ONNX**:

```
artifacts.zip
├── e5-large-pp1875-onnx/          ← модель: onnx/model_quint8_avx2.onnx + токенизатор + конфиги sentence-transformers
├── backend_data/
│   ├── okpd2_synonyms.csv         ← синонимы + формулировки doc2query (если вошли)
│   └── index/<имя>.npz            ← готовый индекс: codes, texts, kinds, vectors (float16)
└── metrics.json                   ← метрики обучения и раздел "onnx" (скорость, косинус, точность int8)
```

### Совместимость с бэкендом (проверено по коду `main`)

| Что | Ноутбук | Бэкенд |
|---|---|---|
| Файл ONNX | `onnx/model_quint8_avx2.onnx` (или `model_qint8_<конфиг>.onnx`), одним файлом без внешних данных | `pick_onnx_file`: avx512_vnni → avx512 → avx2 по флагам процессора; `download_models.py` качает `onnx/*int8*.onnx` |
| Префиксы | имя папки / `HF_REPO` содержит `e5` или `frida` | `prefixes()` по имени модели |
| Пулинг, длина | `1_Pooling/config.json`, `sentence_bert_config.json` (`max_seq_length` 64) | `_Pooled` читает их же |
| Имя индекса | `index_name(EMBED_MODEL, onnx)` — та же формула, что `seed.index_name` | `data/index/<slug>.npz`; `-onnx` добавляется, если slug на него не кончается |
| Формат индекса | `str`-массивы, без pickle | `np.load(allow_pickle=False)` |
| Размерность | 1024 (e5-large), 312 (frida) | `EMBED_DIM` (по умолчанию 1024) |
| Правило иерархии в оценке | `covers` = `matcher.code_covers` (с группами `.X00`/`.000`) | `matcher.code_covers` |

Векторы индекса посчитаны моделью fp32 на GPU, запросы бэкенд кодирует int8 — строка «int8-запросы + fp32-индекс»
в таблице точности ноутбука показывает ровно этот режим. Пересчитать индекс int8-моделью можно `build_index.py`
(ниже, ~20 мин на CPU) и сравнить `eval.py`.

### Вариант А — через Hugging Face (лучше для жюри)

1. В ноутбуке `HF_REPO = "BOBUS2317/e5-large-pp1875-onnx-v2"` (или заменить существующий репозиторий), секрет `HF_TOKEN`.
2. В репозитории: `.env` → `EMBED_MODEL=BOBUS2317/e5-large-pp1875-onnx-v2`; индекс из
   `backend_data/index/bobus2317-e5-large-pp1875-onnx-v2.npz` → `data/index/` (имя печатает ноутбук).
3. Чтобы модель была по умолчанию у всех — `embed_model` в `backend/app/config.py` и аргумент `EMBED_MODEL`
   в `docker-compose.yml`; сборка `docker compose build` скачает только ONNX-файл и токенизатор.

### Вариант Б — локальная папка

1. Распакуйте `e5-large-pp1875-onnx/` в `data/models/` (в git не добавлять, ~560 МБ).
2. `.env`: `EMBED_MODEL=/data/models/e5-large-pp1875-onnx`, `EMBED_BACKEND=onnx` (для frida ещё `EMBED_DIM=312`).
3. `backend_data/index/data-models-e5-large-pp1875-onnx.npz` → `data/index/`,
   `backend_data/okpd2_synonyms.csv` → `data/okpd2_synonyms.csv`.

### Дальше для обоих вариантов

```bash
docker compose build
# индекс: пропустить, если .npz из backend_data/index/ уже в data/index/ (иначе ~20 мин на CPU)
docker compose run --rm -v ./backend:/app -v ./data:/datarw api python scripts/build_index.py --data /datarw
docker compose run --rm -v ./backend:/app api python -m app.seed --reindex
docker compose run --rm -v ./backend:/app -v ./reports:/reports api python scripts/eval.py --testset /data/eval/dev.csv --fit-confidence --out /reports/eval_dev_v2.md
#  → строку CONFIDENCE_COEF=[a, b, c] из вывода записать в .env (или confidence_coef в config.py)
docker compose run --rm -v ./backend:/app -v ./reports:/reports api python scripts/eval.py --testset /data/eval/testset.csv --out /reports/eval_testset_v2.md
docker compose run --rm -v ./backend:/app -v ./reports:/reports api python scripts/eval.py --testset /data/eval/stress.csv --out /reports/eval_stress_v2.md
docker-compose up --build
```

### Когда оставлять новую модель

Сравните с `reports/eval_*_onnx.md` (текущая `BOBUS2317/e5-large-pp1875-onnx`). Оставляем, если вердикт на dev

## 11. Ограничения и что не проверено

- **Если первая ячейка падает на импорте** (`module 'torch' has no attribute ...`, `Ignoring invalid distribution`):
  окружение испорчено прошлой установкой пакетов. Run → **Factory reset** (или перезапуск сессии) и Run All заново.
- **Модель обучается библиотеками новее, чем в бэкенде.** Формат сохранения стандартный, но загрузку в бэкенде
  проверьте до остального (раздел 7). Если не загрузится, поднимем в бэкенде версии sentence-transformers/transformers.
- **Обучение ещё не запускалось.** Ноутбук целиком прогнан на заглушках вместо PyTorch и моделей: данные,
  генерация с продолжением после обрыва, чистка doc2query, метрики, экспорт файлов для бэкенда, ONNX-ячейка.
  Сами циклы обучения, экспорт ONNX и квантизация впервые выполнятся в Kaggle. При ошибке пришлите её текст.
- **ONNX для e5-large.** В fp32 модель больше 2 ГБ, и квантизация sentence-transformers на таких моделях может
  упасть. Тогда ячейка сама переходит на квантизацию onnxruntime с внешним файлом весов. Если не получится и так,
  ячейка напишет ошибку, а модель и остальные артефакты останутся целыми. Для frida этого ограничения нет.
- **Точность «всё в int8»** оценивается по top-50 кандидатам fp32-индекса и только на dev — это приближение.
- Цифры в ноутбуке — без BM25, исправления опечаток и правил бэкенда. Итог — только по `eval.py` бэкенда.
- **doc2query на dev из 88 товаров** — решение «включать или нет» шумное. Окончательно решает `eval.py` бэкенда.
- `dev.csv` маленький (88 товаров), поэтому выбор эпохи по нему шумный. Отсюда правило «не хуже исходной модели» и
  финальная проверка на `holdout`.
- Синтетика и формулировки LLM неидеальны: посмотрите их выборки в выводе ноутбука.
- **Скрипт GigaChat** проверен на имитации API (повторы при 429/401, откат к одиночным запросам, продолжение после
  обрыва, загрузка результатов в ноутбук) и пробами на 20 кодах с настоящим API (`GigaChat-2-Pro`, адреса по
  умолчанию, сертификат из `certs/`): авторизация, JSON-пачки и запись файлов работают, отказов фильтра не было.
  Полный запуск ещё не делался — оценки времени и токенов выше экстраполированы с 20 кодов.
- **Старые результаты GigaChat** (отбор 3 600 кодов по 12 строк) с новым отбором не совпадают. Перегенерируйте их
  новой версией скрипта.
- Позиции ПП с условиями по характеристикам (медизделия по кодам НКМИ, «только в отношении…») правило по коду
  однозначно не разрешает. Бэкенд помечает их `has_conditions`.
